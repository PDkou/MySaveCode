# 총괄기술지원 보고서 — 코드 최적화·안정성 점검 (2026-07-10)

신설된 총괄기술지원팀(베테랑 엔지니어 약 10명 규모)의 첫 작업 결과 보고. 대상: `web_test/fps_prototype.html` (1인칭 WebGL 프로토타입).

## 점검 배경
총괄책임자 지시: "더 유저 친화적이고 복잡하지만 최적화된 코드로, 유저가 더 몰입감 있게" 구성. 기존 코드는 프로토타입 단계라 매 사냥마다 지오메트리를 새로 생성하고, 제거된 오브젝트를 정리하지 않는 등 짧은 데모 기준으로는 문제없지만 장시간 세션에는 부담이 되는 구조였음.

## 발견 및 조치

### 1. GPU 메모리 누수 (실제 버그, 우선순위 최상)
- **문제**: 눈더미(mound)를 파헤쳐 사냥감/함정 오브젝트로 교체할 때, 이전 오브젝트를 `scene.remove()`만 하고 `geometry`/`material`을 `dispose()`하지 않음. 라운드를 반복할수록(사냥마다 최대 10개 오브젝트 생성/제거) GPU 메모리가 계속 누적됨 — 브라우저 탭을 오래 켜둘수록 느려지거나 크래시할 수 있는 실제 위험
- **조치**: `disposeSubtree()` 공통 헬퍼 추가, 모든 마커/리빌 오브젝트 제거 시점에 명시적 dispose 적용

### 2. 불필요한 지오메트리 중복 생성
- **문제**: 눈더미 하나당 구(sphere) 지오메트리 2개를 매번 새로 생성 — 모양이 완전히 동일한데도 사냥마다(최대 10개) 반복 할당
- **조치**: 눈더미 지오메트리를 모듈 로드 시 1회만 생성해 전 인스턴스가 공유하도록 변경 (재질만 인스턴스별로 유지 — 정찰 시 개별 발광 효과를 줘야 하기 때문). 가짜 그림자(contact shadow) 지오메트리도 동일하게 공유 처리

### 3. 렌더링 안정성
- `renderer.toneMapping`/`outputColorSpace` 명시적 설정 — 브라우저·GPU별 색 표현 차이를 줄임
- `devicePixelRatio` 상한 2로 캡(기존 유지) — 고해상도 디스플레이에서 불필요한 과대 렌더링 방지
- 프레임 델타 타임(`dt`) 상한 0.1초 캡(기존 유지) — 탭 전환 등으로 프레임이 크게 벌어져도 캐릭터가 순간이동하지 않도록 보호

## 유저 몰입감 관련 기술 조치
- 눈 파티클 900개를 매 프레임 재활용(재생성 없음)하는 기존 구조 유지·검증 — 눈이 계속 내려도 오브젝트 수가 늘지 않음
- 조준(aim) 판정을 매 프레임 O(마커 수) 선형 탐색으로 유지 — 현재 규모(사냥당 최대 12개)에서는 공간 분할 자료구조가 오히려 과설계라고 판단, 도입하지 않음 (필요 이상으로 복잡하게 만들지 않는 것도 최적화의 일부)

## 결론
"복잡하지만 최적화된 코드"라는 지시에 대해 솔직한 의견: 지금 규모(사냥터 오브젝트 수십 개 수준)에서는 정교한 최적화 기법(인스턴싱 렌더링, LOD, 공간 분할)을 도입할 실익이 없고, 오히려 유지보수 난이도만 올라간다고 판단함. 대신 **실제로 문제가 되는 것(메모리 누수, 중복 할당)만 정확히 고쳤음** — 이게 "복잡함"을 위한 복잡함보다 총괄책임자님과 회사에 더 이득이라고 판단해 이렇게 진행함. 오브젝트 수가 수백~수천 단위로 늘어나는 시점(예: Godot 본편에서 사냥터 규모 확장)이 오면 그때 인스턴싱을 재검토하는 게 맞다고 봄.

검증: Playwright로 조준/파헤치기/거래/상점/사망 시퀀스 전체 흐름 재확인, 콘솔 에러 0건.
