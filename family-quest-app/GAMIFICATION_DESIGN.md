# 게임화 시스템 설계 문서 (v1, 4단계 모두 구현 완료)

이 문서는 다음 세대 게임화 시스템(포인트/경험치 분리, 의뢰 기반 포인트, 방치형 타이쿤, 상점, 캐릭터,
칭호)의 설계를 정리한 것입니다. 대화로 하나씩 결정된 내용을 모아둔 것으로, **1~14번은 설계 당시
작성한 원문 그대로 보존**했습니다 (구현하면서 세부가 조금씩 달라진 부분은 15번 "구현 현황"에서
실제 코드 기준으로 정리했으니, 설계 의도는 여기서·정확한 현재 상태는 15번에서 확인하세요).

**구현 상태**: Phase 1~4 전부 구현되어 `claude/family-quest-app-v01-3aw1ro` 브랜치에 머지됨
(PR #62·#63·#64·#65). 자세한 내용은 15번 참고. 지금 배포된 `complete_task`/`reopen_task`는 이 문서
3~5번(배정방식 3종 + 의뢰자 보너스 + 자기어뷰징 방지)을 그대로 구현한 상태이며, 예전 "완료 시 +10
고정 포인트" 방식(PR #101)은 더 이상 쓰이지 않습니다.

## 1. 정체성 원칙

이 앱의 핵심은 "누군가 의뢰하고 누군가 달성한다"입니다. 모든 규칙은 이 원칙에서 파생됩니다:
**의뢰자가 자기 의뢰를 스스로 달성해도 명성(완료 횟수/스트릭/뱃지/주간 MVP)은 오르지 않습니다** —
협업(모두형) 예외를 빼면요. 포인트(화폐)와 명성(순수 기록/랭킹)은 각각 다른 조건으로 지급되므로
반드시 분리해서 생각해야 합니다.

## 2. 화폐 체계: 포인트 vs 경험치 vs 방치형 재화

세 가지를 분리합니다:

- **포인트**: 의뢰(퀘스트)를 걸고 받는 소비 가능한 화폐. 상점에서 소비됨. 방마다 별도 잔액
  (`family_members`처럼 `(user_id, family_id)` 단위).
- **경험치**: 레벨 표시용, 소비되지 않고 계속 누적. 포인트를 벌 때 별도로 같이 오름 (지금처럼
  "레벨/다음 레벨까지" 표시에 사용). 명성 지표(완료 횟수/스트릭/뱃지/MVP)와 함께 움직임.
- **방치형 재화(타이쿤 화폐)**: 아래 6번 참고. 포인트와는 완전히 다른 화폐. 포인트로 못 바꾸고,
  포인트 → 방치형 화폐도 안 됨(한쪽 방향만 열림, 6-4번 참고).

**포인트의 유입 통로는 딱 두 가지뿐입니다**: (a) 퀘스트를 통해 벌기, (b) 방치형 재화를 포인트로
교환하기. 그 외 포인트가 시스템에서 임의로 생성되는 경로는 없습니다 (의뢰자 보너스도 "새로 찍어내는"
것처럼 보이지만 실제로는 4번의 조건 하에서만, 소량만 발생 — 완전한 무제한 발행이 아님).

## 3. 퀘스트 배정 방식 3종

기존에는 "특정인 지정" / "모두"만 있었는데, "모두"가 실제로는 서로 다른 두 가지 의미로 쓰이고
있었다는 걸 발견해서 셋으로 나눕니다. **새 필드는 필요 없음** — `task_assignees`에 담긴 인원수만으로
셋 다 구분됩니다:
- 담당자 0명 → 선착
- 담당자 수 = 현재 방 인원수(전원) → 모두
- 그 사이(1명 이상, 전원 미만) → 특정인 지정

기존 "담당자 지정 안 함" UI 옵션이 자연스럽게 선착으로 재해석됩니다 (라벨만 "선착순"으로 변경).

| 방식 | 의미 | 포인트 지급 | 명성(완료횟수/스트릭/뱃지/MVP) |
|---|---|---|---|
| **특정인 지정** | 의뢰자가 특정 1인 이상을 콕 집어 배정 | 완료자가 건 포인트 전액 수령 | 의뢰자≠완료자일 때만 인정 |
| **모두** (협업) | 배정된 전원이 같이 하는 일 | 건 포인트를 배정 인원수로 N분의 1 | **의뢰자 포함 전원 인정** — 다같이 한 일이므로 의뢰자가 그 안에 끼어 있어도 명성 오름 |
| **선착** (경쟁) | 먼저 하는 사람이 전액 독식 | 완료자가 전액 수령 | 의뢰자≠완료자일 때만 인정. **의뢰자 본인이 셀프로 채가면 포인트도 명성도 0** (건 포인트 그대로 돌려받을 뿐, 이득도 손해도 없음) |

1인 개인방은 예외입니다 — 물어볼 상대가 없으므로 위 표와 무관하게 항상 포인트·명성 둘 다 정상 지급.

## 4. 의뢰자 보너스 (소량 환급)

- **특정인 지정 의뢰에서만** 적용. 모두형/선착형은 대상 아님.
- 조건: 의뢰자 ≠ 완료자, 그리고 완료됨.
- 금액: 건 포인트의 **10%**. 단 건 포인트가 **10 미만이면 보너스 없음**.
- 재원은 완료자가 받는 몫에서 깎는 게 아니라 시스템이 별도로 얹어주는 개념 (그래서 전체 경제가
  아주 소폭 인플레이션 — 실제 의뢰↔완료 거래가 일어날 때만 발생하므로 건전한 인플레이션으로 간주).

## 5. 자기어뷰징 방지 매트릭스 (최종)

| 상황 | 포인트 | 명성 |
|---|---|---|
| 특정인 지정, 의뢰자=완료자로 지정 (사실상 셀프) | 0 | 0 |
| 특정인 지정, 의뢰자≠완료자 | 전액 + 의뢰자 10% 보너스 | 완료자만 인정 |
| 모두형, 의뢰자 포함 전원이 나눠 가짐 | 각자 N분의 1 (의뢰자 본인 몫 포함) | **전원 인정 (의뢰자 포함)** |
| 선착형, 의뢰자 본인이 셀프로 채감 | 0 (건 만큼 그대로 회수, 이득 없음) | 0 |
| 선착형, 제3자가 채감 | 완료자 전액 (의뢰자 보너스는 없음) | 완료자만 인정 |
| 1인 개인방 (모든 경우) | 정상 지급 | 정상 지급 |

## 6. 방치형 타이쿤 (쿠키클리커 스타일)

### 6-1. 기본 구조
- 화면 켜져 있을 때 자동 생산(초당) + 탭 시 보너스, 오프라인 동안도 경과 시간만큼 누적 지급
  (최대 24시간까지만 인정 — 그 이상 방치해도 추가 누적 없음).
- 재화 자체는 쿠키클리커처럼 숫자가 크게, 화려하게 커져도 무방 (장르 특성상 UX적으로 오히려 권장).
- 업그레이드: 5~10단계, 비용은 지수 증가(예: 이전 단계 비용 × 1.15), 각 단계 생산량 증가.
  콘텐츠는 나중에 계속 확장 가능하게 설계 (건물/업그레이드 종류 추가 등).

### 6-2. 기준 수치 (1차 초안, 추후 밸런스 테스트로 조정)
- 기본 생산량: 분당 10코인 (완전 무업그레이드 기준, 하루 방치 시 약 14,400코인).

### 6-3. 포인트 교환
- 방향은 **타이쿤 화폐 → 포인트만 가능** (역방향 없음).
- **하루 교환 상한 있음** (자정 리셋). 목적: 방치만 해도 의뢰 활동을 최소한 유지할 수 있게(퀘스트를
  전혀 못 해도 의뢰 몇 건은 걸 수 있는 정도), 그러나 실제로 퀘스트를 완료하는 것보다는 훨씬 비효율적으로.
- 상한 수치는 스테이크(건 포인트)가 가변이라 정확한 "하루 몇 건치"로 못 박기 어려움 — **1차로 하루
  20~30포인트 정도로 잡고 실사용 데이터로 조정**하는 것으로 잠정 결정.
- 방치형 재화의 자체 경제(생산 곡선, 업그레이드)는 화려하게 키워도 되지만, **포인트로의 실제 전환량은
  이 하루 상한이 항상 최종 안전장치** — 재화가 억 단위로 쌓여도 포인트 전환은 상한을 못 넘음.

### 6-4. 확인된 원칙
- 방치형은 퀘스트의 대체재가 아니라 보조 수단. 퀘스트 완료가 항상 압도적으로 효율적이어야 함.

### 6-5. 타이쿤 상점 (7번 상점 체계와 연결)
타이쿤 화면 안에 자체 상점이 있습니다. 안에 섞여 있는 것:
- **타이쿤 자체 업그레이드/생산 요소** — 캐릭터 아이템이 아니라 순수 타이쿤 내부 진행용 (6-1의
  업그레이드 단계들). `shop_items`(7번) 카탈로그와는 무관.
- **"포인트로 바꾸기" 항목** — 6-3번 교환(하루 상한 있음)을 이 상점 화면 안의 구매 항목처럼 노출.
- **가끔 타이쿤 화폐 전용 한정 패션 아이템** — `shop_items`에 속하되 `currency='tycoon'`인 것들.
  포인트 상점보다 등장 빈도는 낮은, 보너스/한정판 성격.

## 7. 상점 / 캐릭터 시스템

- **캐릭터는 방(family)별로 별도** — 같은 사람이라도 가족방/개인방/회사방마다 캐릭터가 다름.
  이유: 방마다 소속감을 분리해서 느끼게 하기 위함. 스키마도 지금 `family_members.points`처럼
  `(user_id, family_id)` 단위로.
- **v1은 전부 코스메틱** — 무기/방패 등 이름은 RPG 장비 느낌이지만 스탯(공격력 등) 없음, 순수 겉모습.
  스탯이 있는 "진짜 장비" + 그 위에 덧씌우는 "스킨" 분리는 나중에 스탯 시스템을 넣을 때 재검토
  (아이디어로만 보관 — 슬롯이 실질적으로 2배로 늘어남, `weapon`/`weapon_skin`처럼).
- **슬롯 (11개)**: `body`(기본색) · `head` · `background` · `title`(칭호, 아래 8번 참고) ·
  `weapon` · `shield` · `accessory1` · `accessory2` · `shoes` · `top` · `pants`.
  슬롯당 아이템 하나만 장착.

### 7-1. 스키마 초안
- **`shop_items`** (전역 카탈로그, 방 구분 없음): `id`, `slot`, `name`, `sprite_key`(placeholder
  렌더링용 식별자, 나중에 실제 아트로 교체 시 매핑만 바꾸면 됨), `acquisition_type`(`purchase` |
  `title_condition`), `currency`(`points` | `tycoon`, `purchase`일 때만 의미 있음), `price`(purchase일
  때만), `sort_order`.
- **`member_owned_items`**: `(user_id, family_id, item_id)` — 소유 여부. **방별로 독립** (A 방에서
  산 아이템이 B 방 캐릭터엔 안 붙음 — 화폐가 이미 방별로 분리돼 있으니 자연스러운 연장).
- **`member_equipped_items`**: `(user_id, family_id, slot)` → 현재 장착한 `item_id`. 슬롯당 최대 1개.

### 7-2. 구매 상점 두 종류
- **포인트 상점**: 패션 아이템 위주(`currency='points'`) — 캐릭터 꾸미기의 메인 창구.
- **타이쿤 상점**: 6-5번 참고.

### 7-3. 렌더링
- 이미지 파일 없이 슬롯별 색/도형 정보만으로 SVG/CSS 기반 도트 캐릭터를 코드로 그림. 실제 아트가
  생기면 `sprite_key` 매핑만 교체 (10번 참고).

## 8. 칭호 시스템

- 경험치 누적으로 얻는 칭호 + 특정 조건 달성으로 해금하는 칭호, 두 경로 모두 존재.
- 조건부 칭호는 **조건의 절반 정도 도달했을 때부터 "잠긴 칭호"로 미리보기 노출** (동기부여 장치).
- **장착 가능** — 7번의 `title` 슬롯을 통해 캐릭터에 표시. 그래야 칭호를 얻는 것 자체가 눈에 보이는
  보상이 됨.
- 기존에 이미 배포된 `member_badges`(뱃지 갤러리, 트로피 케이스 성격)는 그대로 유지하고 건드리지 않음.
  칭호는 `shop_items`에 `acquisition_type='title_condition'`으로 별도 등록하고, 조건 달성 시
  `member_owned_items`에 자동으로 소유권이 생기는 방식 (뱃지 해금 트리거 로직과 같은 지점에서,
  뱃지랑 칭호를 동시에 지급하는 식으로 연결 가능).
- **완전 히든 칭호**도 있음 — 8번의 "50% 프리뷰"와는 별개 카테고리. 조건 자체를 아예 안 보여주고
  달성 시 서프라이즈로 공개 (달성 전엔 존재 여부도 노출 안 함).
- 전체 목록은 12번 참고.
- 우선순위 낮음 — 화폐/의뢰 시스템 확정 이후에 붙여도 되는 부분.

## 9. 회사방 게임화 커스터마이징 (백로그, 미확정)

- 이진 토글(켜기/끄기)이 아니라, 회사마다 필요/불필요가 다를 수 있으므로 **세분화된 커스텀 옵션**으로
  가는 게 맞다는 방향만 잡음. 구체적으로 어떤 항목을 개별 on/off 할 수 있게 할지는 미정.
- 아직 실제로 이 기능을 파는 단계가 아니므로, 화폐/의뢰 시스템이 먼저 확정된 뒤 다시 논의.

### 신규 인프라가 필요한 것 정리
대부분은 기존 테이블(`tasks`/`task_comments`/`task_activities`/`quest_payouts`/`family_members`)에
대한 새 쿼리만 짜면 되고, 진짜로 새 컬럼/로직이 필요한 건 딱 하나입니다: **"다함께 스트릭"** (방
단위로 모두형 완료의 연속일수를 추적하는 카운터 — 개인 스트릭과 별개로 새로 만들어야 함). 나머지
"신규"로 표시된 항목들은 컬럼 추가 없이 기존 컬럼들을 조합한 쿼리로 가능합니다.

### 검토가 특히 필요한 부분
- **이름만으로 의미를 추정한 항목**: 후한 인심/큰손/전담마크/믿음의 리필/단골 사장님/우리집
  챔피언/무패행진 등 — 원래 의도와 다르게 해석했을 가능성이 있습니다.
- **개념이 겹치는 항목**: 무패행진과 독보적 존재(둘 다 선착 누적), 부지런한 새와 얼리버드 헌터(둘
  다 아침 시간대) — 통합하거나 조건을 더 차별화할지 결정 필요.
- **"우리집 챔피언"의 리더보드 방식**: 순위가 바뀌어도 한 번 얻은 칭호는 유지되는 "스냅샷" 방식으로
  제안했는데, 이게 맞는 방향인지 확인 필요.

## 15. 구현 현황 (2026-07-28 기준)

이 설계를 실제로 구현한 4개 PR과, 설계 대비 실제로 뭐가 들어갔고 뭐가 백로그로 남았는지 정리.
**이 섹션이 "지금 실제로 뭐가 되어 있는지"에 대한 가장 정확한 출처**입니다 — 1~14번은 설계 당시
기록이라 세부 수치나 범위가 실제 구현과 다를 수 있습니다.

### Phase 1 — 경제 리라이트 (PR #62)
- `family_members.xp` 신설(레벨 계산은 이제 `points`가 아니라 `xp` 기준), `tasks.stake_points`,
  `quest_payouts` 원장 테이블(모두형처럼 한 완료 이벤트가 여러 명에게 동시에 지급될 수 있어서 필요).
- `create_task`/`complete_task`/`reopen_task`를 3~5번 설계(배정방식 3종, 의뢰자 10% 보너스,
  자기어뷰징 방지 매트릭스) 그대로 재작성.
- 설계와 차이 없음 — 1:1 구현.

### Phase 2 — 상점 / 캐릭터 (PR #63)
- `shop_items`/`member_owned_items`/`member_equipped_items` + `purchase_item`/`equip_item`/
  `unequip_item` RPC. 슬롯 11개(7번) 그대로.
- **캐릭터 렌더링**: 아직 실제 아트 없음(10번 설계대로) — `CharacterSprite.tsx`가 슬롯별 색상
  hex/이모지 조합만으로 그리는 placeholder. `sprite_key` 매핑만 나중에 교체하면 되는 구조는 유지.
- **상점 콘텐츠**: 스타터 세트 ~35개만 시딩 (11번 백로그 그대로 남음 — "나머지 아이템 목록"은 미정).

### Phase 3 — 칭호 (PR #64)
- `grant_title()` 내부 RPC + `award_quest_payout`/`purchase_item`/`create_family_room`/
  `join_family_room`에서 조건 충족 시 자동 호출하는 구조.
- **설계 대비 축소**: 12번에서 확정한 76개 중 **12개만 구현** (특정인/모두/선착 각 1·10·50회
  달성 9종 + `newcomer` + `xp_1000` + `shop_regular`). 나머지 64개는 13번의 새 트래킹(A~F)이 있어야
  가능한 것들이라 "일단 아예 안 되는 건 빼고, 기능 추가해서 끝날 것만" 원칙으로 이번 범위에서 제외.
  즉 12번 목록 자체는 여전히 유효한 최종 목표이고, 인프라(칭호 = `shop_items` 행 + `grant_title`
  호출 지점 추가)는 이미 갖춰져 있어서 나머지는 "트래킹 붙이고 호출 한 줄 추가"만 하면 되는 상태.

### Phase 4 — 방치형 타이쿤 (PR #65)
- `tycoon_state` + `sync_tycoon_currency`(내부, 지연 정산) + `collect_tycoon_currency`/
  `tap_tycoon_currency`/`upgrade_tycoon`/`exchange_tycoon_currency`. 6번 설계 그대로.
- 확정한 수치(6-2/6-3의 "1차 추정치"): 분당 10코인(레벨당 +10, 최대 레벨10=분당110), 탭 +3(쿨다운
  2초), 업그레이드 비용 `100 × 1.15^레벨`, 교환 비율 1000코인=1포인트, **하루 교환 상한 25포인트**로
  확정(6-3에서 "20~30 사이"로 뒀던 걸 25로 픽스 — 실사용 데이터 없이 잠정 결정한 값이라 조정 여지 있음).
- 타이쿤 상점(6-5): `tycoon_maxed` 칭호(레벨10 달성) + 타이쿤 화폐 전용 패션 아이템 3개 시딩.
- 클라이언트: `TycoonModal`(탭/업그레이드/교환/타이쿤 상점 통합 화면, 화면 열려있는 동안 로컬로
  숫자가 올라가는 연출 포함) + 상단바 💰 아이콘.

### Phase 5 — 상점 콘텐츠 확장 + 칭호 트래킹 A~D (2026-07-28)
- **상점 콘텐츠 확장**: 11번 백로그 중 "상점 아이템 콘텐츠 확장"을 처리. 포인트 화폐 코스메틱 20종을
  10개 슬롯(칭호 제외)에 추가 시딩 — 각 슬롯의 기존 `sort_order`를 이어받는 방식. 여전히 "완전한
  최종 카탈로그"는 아니고 스타터+배치2 수준.
- **13번 A/B/D 트래킹 신설 + C는 대안으로 구현**:
  - (A) 접속 로그: `family_members.last_seen_date`/`login_streak` + `record_login()` RPC(앱 세션당
    1회 호출, 이미 오늘 기록했으면 no-op). 7일 연속 시 `settler`(정착민) 칭호 자동 부여.
  - (B) 생일: `profiles.birthday` 추가 + 설정 화면에 입력 UI. 선착 완료 순간 오늘 날짜와 일치하면
    `birthday_gift`(생일 선물, 완전 히든) 칭호 부여.
  - (C) 실시간 접속 현황: **설계를 Realtime Presence에서 heartbeat 근사치로 변경**. Presence 채널
    상태는 realtime 서버 프로세스에만 있고 Postgres 함수에서 조회 자체가 불가능해서, 대신
    `family_members.last_heartbeat_at`을 클라이언트가 ~25초 간격으로 갱신(`tap_heartbeat()` RPC)하고
    "90초 이내 갱신 = 지금 접속 중"으로 판정. 모두형 퀘스트 완료 시 배정자 전원이 이 조건을
    만족하면 `together_now`(한자리에, 완전 히든) 칭호를 전원에게 부여.
  - (D) 주간 MVP: 기존 알림용 Edge Function(`send-due-reminders`)은 이 저장소 소스 밖(Supabase
    대시보드로 배포)이라 거기 얹지 않고, `compute_weekly_mvp()`를 완전히 독립적인 Postgres 함수로
    작성해 `schema.sql` 안에서 `pg_cron`으로 직접 스케줄(매주 월요일 00:05). `pg_cron`이 활성화 안 된
    프로젝트에서도 스키마 실행 자체는 끝까지 통과하도록 `raise notice`로만 막는 방어 블록 포함(파일
    내 다른 pg_cron 블록과 동일 패턴). 가족별 주간 1위(보상 지급된 완료 수 기준) 집계를
    `weekly_mvp_log`에 기록, 통산 3회 달성 시 `solidarity`(연대감) 칭호 부여.
  - 신규 칭호 5종 시딩: `settler`/`night_login`(올빼미 접속자, 새벽 2~5시 접속, 완전 히든)/
    `birthday_gift`/`together_now`/`solidarity`. `night_login`/`birthday_gift`/`together_now`는
    "완전 히든 칭호"(8번) 원칙에 맞춰 `shop_items.hidden` 컬럼을 신설해 미보유 시 상점 목록 자체에
    아예 안 보이도록 클라이언트에서 필터링.
  - **12번 목록 기준 진행 상황**: 76개 중 이제 Phase 3(12개) + Phase 4(`tycoon_maxed` 1개) +
    Phase 5(5개) = 18개 구현 (이전 버전에서 `tycoon_maxed`를 빼먹고 17개로 잘못 셌던 걸 바로잡음).
    나머지 58개의 조건 초안은 13-2번 참고 — 다음 스텝은 그 초안을 사용자와 함께 검토/확정하는 것.

### Phase 6 — 칭호를 상점에서 분리 + 뱃지 장착 (2026-07-29)
- **칭호 UI 분리**: 칭호는 원래부터 구매 불가(항상 `title_condition`)였는데도 상점 모달의 탭으로
  보여서 "판매 중인 것"처럼 보인다는 피드백 → `MyStatsModal`(나의 기록)의 뱃지 컬렉션 옆에
  "칭호 컬렉션"으로 이동. 잠김/해금 그리드 + 보유한 것만 장착/해제 가능, 상점에는 더 이상 칭호 탭 없음.
- **뱃지도 장착 가능하게**: "뱃지도 칭호처럼 평소에 보여줄 수 있으면 더 재밌겠다"는 피드백 반영.
  `family_members.equipped_badge_key text`(닉네임처럼 한 번에 하나만) + `equip_badge`/
  `unequip_badge` RPC(소유 검증 포함) 신설. 뱃지는 `shop_items`가 아니라 `member_badges`라서
  `member_equipped_items`(아이템 전용)를 재사용할 수 없어 별도 컬럼으로 처리.
- **표시 슬롯 분리**: "칭호는 텍스트 틀, 뱃지는 별도 칸으로 나눠야 할 것 같다"는 요청대로, 캐릭터
  미리보기 옆에 칭호는 알약 모양 프레임(텍스트), 뱃지는 원형 아이콘 칩으로 서로 다른 슬롯에 표시
  (`shop-equipped-title-frame` / `shop-equipped-badge-slot`).
- 로컬 Postgres로 `equip_badge`(소유 뱃지 장착 성공 / 미소유 뱃지 장착 시 `item_not_owned` 거부)와
  `unequip_badge` 모두 검증 완료.

- 회사방 게임화 커스터마이징 세부 항목 (9번, 방향만 정하고 미정).
- 타이쿤 밸런스 수치 조정 (6-2/6-3, 실사용 데이터 필요).
- 스탯 있는 "진짜 장비" + 스킨 분리 (7번, 나중에 스탯 시스템 넣을 때 재검토).
- RLS 정책 문구 정밀화.
- 타이쿤 상점 아이템 실제 구매 흐름 QA (16번에서 로직 자체는 검증했지만, 실제 클라이언트 UI로는
  아직 안 눌러봄).

## 16. 알려진 리스크 / 실행 전 확인 필요

- **`schema.sql`을 실제 Postgres 16에 대고 검증 완료** (2026-07-28). 이 개발 세션 환경에 `psql`과
  로컬 PostgreSQL 16 서버가 설치되어 있다는 걸 뒤늦게 발견해서, Phase 1~4를 포함한 병합된
  `schema.sql` 전체를 실제로 실행해봤습니다:
  - `auth.users`/`auth.uid()`, `storage.buckets`/`storage.objects`, `authenticated`/`anon`/
    `service_role` 롤, `supabase_realtime` publication, `net.http_post`(pg_net) 등 Supabase가
    플랫폼 차원에서 미리 만들어주는 것들만 최소 스텁으로 채워 넣고, **스키마 파일 자체는 한 글자도
    수정하지 않고** 그대로 실행 — 처음 두 번은 이 스텁들이 부족해서 실패했고(스텁 문제였지 스키마
    문제가 아님), 스텁을 채운 뒤로는 **전체 스키마가 에러 없이 한 번에 실행 완료**됐고, **두 번째
    재실행도 에러 없이 통과**해 idempotency도 확인됨.
  - 여기서 Phase 4의 `purchase_item`이 `tycoon_state`를 forward-reference하는 문제(위 Phase 4
    섹션에서 스칼라로 우회한 그 부분)가 실제로 문제없이 `CREATE FUNCTION`을 통과하는 것도 확인.
  - **기능 테스트도 실행**: 가짜 유저 2명으로 특정인 지정 퀘스트에 10포인트를 걸고 완료 → 완료자
    전액(+10P +10XP) + 의뢰자 10% 보너스(+1P, 명성 없음) 정확히 지급 확인 → `reopen_task`로
    되돌렸을 때 두 사람 모두 정확히 원상복구 확인. 타이쿤 쪽도 `tap`(2초 쿨다운 포함) →
    `upgrade`(비용 100, 레벨 1로) → `exchange`(1000코인=1포인트, 25포인트 정확히 하루 상한에서
    멈춤, 그 이상 요청 시 `daily_cap_reached`) → 타이쿤 화폐로 `purchase_item` 성공까지 전부
    설계한 숫자 그대로 재현됨.
  - **한계**: 이건 순정 Postgres 16 + 최소 스텁 환경입니다. 진짜 Supabase 프로젝트의 RLS는 세션의
    JWT 클레임으로 `auth.uid()`가 채워지는데, 여기서는 세션 변수로 흉내만 냈습니다. `pg_net`의
    실제 HTTP 전송, Supabase Storage의 실제 정책 적용, 실제 Auth 트리거 타이밍 등은 검증 범위 밖.
    그래도 스키마 문법/제약조건/RPC 비즈니스 로직 정확성은 이제 "눈으로 재검토"가 아니라 실제
    실행으로 확인된 상태 — 배포 전 스테이징에서 한 번 더 돌려보는 걸 권장하지만, 리스크는 이전보다
    크게 낮아졌습니다.
- **참고(버그 아님)**: 검증 중 `notify_task_activity_event`/`notify_task_comment_event`(퀘스트
  생성/완료/재오픈/댓글 시 웹훅을 쏘는, 이번 세션 이전부터 있던 기존 트리거)가 실제 프로젝트 URL과
  `sb_publishable_...` 키를 스키마 파일에 하드코딩해두고 있는 걸 발견했습니다. Supabase의
  `publishable` 키는 원래 클라이언트에 노출돼도 안전하도록 설계된 키라 그 자체가 비밀 유출은
  아니지만, URL이 프로젝트 ref로 고정돼 있어서 **스테이징/테스트 DB에서 이 스키마를 그대로 돌리면
  테스트용 퀘스트 생성/완료 이벤트가 실제 프로덕션 Edge Function으로 그대로 전송됩니다.** 스테이징
  환경에서 검증할 때는 이 부분을 인지하고 있어야 합니다 (`supabase/schema.sql`에서
  `rapid-service` 검색하면 두 군데 나옵니다).
