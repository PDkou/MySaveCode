## 1. 개요

- **컴퍼니퀘스트는 family-quest-app과 완전히 동일한 코드베이스를 쓰는 별도 앱**입니다.
  `business-quest-app/`은 `@core` Vite alias로 `family-quest-app/src`를 그대로 참조하는
  얇은 래퍼(`vite.config.ts`)이고, 앱 모드는 `VITE_APP_MODE=business` 환경변수 하나로 결정됩니다
  (`src/lib/appMode.ts`). 새 기능은 원칙적으로 `family-quest-app/src`에 한 번만 작성하면 두
  앱 모두에 반영됩니다.
- 대상은 **B2B, 회사/팀 단위 업무 퀘스트(할일) 관리**입니다. family-quest-app이 가정 내
  집안일 분배용이라면, 이건 팀 업무 분배/추적용입니다.
- 2026-08부터 가족용/회사용이 완전히 분리된 두 개의 앱으로 배포됩니다 (그 이전엔 한 앱 안에서
  `room_type`만 다르게 쓰던 시기가 있었으나 지금은 도메인부터 별도).

## 2. family-quest-app과 공유하는 것 / 다른 것

**공유** — 코드가 완전히 같으므로 대부분의 기능이 그대로 공유됩니다:

- 퀘스트 관리 코어 로직(생성/배정/완료/반복/스테이킹), 게임화(포인트/XP/레벨/스트릭/뱃지/칭호),
  가족방 채팅, 알림(인앱 + 푸시), 캘린더/사진첩, 설정, PWA — 전부 family-quest-app과 동일.
- 게임화 로직은 `room_type`을 구분하지 않고 완전히 동일하게 동작합니다 (`CORE_APP_DESIGN.md`
  14번) — 포인트/XP/칭호 체계가 회사방이라고 다르게 계산되지 않음.

**다른 것** — 회사방(`room_type='business'`) 전용으로 갈라지는 지점:

- **CSV 리포트**: 주간 리포트 모달(`WeeklyBreakdownModal`)에 CSV 다운로드 버튼이 회사방에서만
  뜸. 완료된 퀘스트의 제목/담당자/완료일시를 내보내고, 엑셀 한글 깨짐 방지로 UTF-8 BOM을 붙임
  (`CORE_APP_DESIGN.md` 14번).
- **방 생성 슬롯 제한이 적용 안 됨**: family-quest-app은 방 생성 슬롯이 기본 1개(광고 제거
  구매마다 +1)로 제한되지만, `room_type='business'` 방 생성은 이 체크 자체를 건너뜁니다
  (`schema.sql`의 `create_family_room` -- `if v_room_type = 'family' then` 블록 안에서만
  슬롯 카운트를 확인).
- **생일 필수 입력 / 광고 대상 아님**: family-quest-app은 미성년 이용자 대응 목적으로 회원가입
  시 생일을 필수로 받지만(`APP_MODE === 'family'`로 게이팅), 컴퍼니퀘스트는 B2B 앱이라 이
  체크가 아예 꺼져 있습니다. 광고 기반 수익화 대신 구독 결제로 갑니다 (5번 참고).
- **방 생성 시 지급되는 칭호**: 회사방을 만들면 생성자에게 `boss`(사장님) 칭호가 즉시 추가로
  지급됩니다 (`create_family_room`, `room_type='business'`일 때만).
- **문구/브랜딩**: 3번 참고.

## 3. 브랜딩 · 문구

가족 중심 단어("가족"/"가족방")를 팀 중심 단어("팀"/"팀 공간")로 바꾼 문구 오버라이드가
`src/i18n/businessOverrides.ts`에 있습니다. `ko.json`/`ja.json`을 통째로 복사해서 고치는 게
아니라, `APP_MODE === 'business'`일 때만 특정 leaf 키를 덮어쓰는 방식(`deepMergeLocale`) --
조사(을/를, 이/가 등)가 단어마다 다르게 붙어서 기계적 치환이 아니라 손으로 다시 쓴 문장들입니다.

- 앱 이름: "Company Quest" / 태그라인: "팀과 함께하는 업무 퀘스트"
- "가족방" → "팀 공간", "가족" → "팀", "방장" → (건드리지 않음, 기존에도 미번역 상태였음)
- 축하 메시지, 도움말 본문, 주간 리포트 제목, 뱃지 이름("50개 퀘스트" 뱃지 → "팀의 영웅"),
  채팅("가족 채팅" → "팀 채팅") 등도 전부 오버라이드됨
- 한국어/일본어 둘 다 별도로 작성 (`ko`/`ja` 각각)

## 4. 배포

`README.md` "3-2. 회사용 앱(business-quest-app) 별도 배포" 참고. 요약:

- Vercel에 family-quest-app과는 **완전히 별개인 새 프로젝트**를 하나 더 만들어서 배포 --
  같은 GitHub 저장소를 다시 import, **Root Directory를 `business-quest-app`으로 지정**.
- 환경변수는 family-quest-app과 **`VITE_SUPABASE_URL`/`VITE_SUPABASE_PUBLISHABLE_KEY` 등
  완전히 같은 값**을 그대로 씀 (같은 Supabase 백엔드를 공유) -- 딱 하나, **`VITE_APP_MODE=
  business`** 만 추가로 필요. 이걸 안 넣으면 회사용 앱이 가족용처럼 동작함.
- 배포된 새 도메인을 Supabase Authentication → URL Configuration의 Redirect URLs에
  **추가**(family-quest-app 주소는 지우지 않고 같이 등록).
- 두 프로젝트 다 같은 저장소/브랜치를 보고 있으므로 푸시 한 번으로 두 앱 다 재배포가 트리거됨
  -- 다만 **2026-09까지는 business-quest-app 쪽이 `family-quest-app/src`(`@core`로 가져다
  쓰는 공유 소스)만 바뀐 커밋에서 매번 "Skipped - Not affected"로 스킵되는 문제가 있었음**.
  Vercel의 기본 Ignored Build Step이 프로젝트의 Root Directory(`business-quest-app`) 안의
  변경만 감지하고, `@core` alias로 참조하는 바깥 디렉터리는 못 봤기 때문 -- `business-quest-
  app/vercel.json`에 `family-quest-app/src`/`package-lock.json`까지 함께 확인하는
  `ignoreCommand`를 명시해서 고침. 대시보드에 수동으로 설정해둔 Ignored Build Step 값이
  이미 있었다면 이 파일이 그걸 덮어쓸 수 있으니, 배포 후 한 번 대시보드에서 충돌 없는지
  확인해두는 게 안전함.
  - **`git diff HEAD^ HEAD`가 아니라 `$VERCEL_GIT_PREVIOUS_SHA`를 기준으로 비교**합니다 --
    이 저장소는 이 세션 내내 "기본 브랜치를 merge로 받아온 뒤 푸시"하는 워크플로를 써서, 브랜치
    HEAD가 거의 항상 머지 커밋입니다. 머지 커밋의 `HEAD^`(첫 부모)는 보통 이미 그 변경분을
    포함하고 있는 커밋이라(머지 자체가 아니라 그 이전 커밋에서 실제 변경이 일어났으므로),
    `HEAD^ HEAD` 비교로는 아무 차이가 안 보여서 매번 스킵으로 오판하는 문제가 실제로
    있었습니다(PR #279에서 고치는 도중 그 PR 자체에서 재현/발견) -- 직전 배포 시점의 실제 커밋을
    가리키는 `VERCEL_GIT_PREVIOUS_SHA`로 비교해야 머지 커밋 워크플로에서도 정확합니다. 이
    값이 없는 경우(그 브랜치의 첫 배포 등)는 안전하게 "빌드함"(스킵 안 함) 쪽으로 기본값을
    잡아뒀습니다.

## 5. 수익화 (B2B 구독) — 요약

전체 근거는 `MONETIZATION_DESIGN.md` 2번. **현재 방향만 정해짐, 코드 착수 전(📋)**:

- 스토어(Google Play/App Store) 미판매, **B2B 직판** — Stripe/Komoju 등으로 자체 구독 결제.
  스토어 IAP 정책을 신경 쓸 필요가 없다는 게 family-quest-app과의 가장 큰 구조적 차이.
- **1개월 무료 체험**.
- 요금제는 **정원 기준 3단계**: Standard(~50명) / Pro(~300명) / Premium(~1000명), 플랜이
  오를수록 인당 단가도 함께 오르는 구조 (Standard 참고치 인당 ~300엔, Pro/Premium 단가는
  아직 미정).
- CSV 리포트/파일첨부는 이미 구현되어 있음(2번 참고) — 새로 할 일은 파일첨부 8MB 상한을
  플랜별로 차등 적용하는 것 정도.
- 아직 안 정해진 것: 결제대행사 선정(Stripe vs Komoju), Pro/Premium 정확한 인당 단가,
  `subscriptions`/좌석 제한 등 실제 DB 스키마.

## 6. 사원 관리 (출퇴근/휴가) — 요약

전체 설계는 `EMPLOYEE_MANAGEMENT_DESIGN.md` (5번과 완전히 독립적으로 설계 -- "결제 구조와
묶지 않는다"고 명시). **일본 노동기준법을 기본 전제로 설계, 순수 설계 단계(코드/DB 착수 전)**:

- **체크인**: GPS 위치 기반 + QR 스캔 둘 다 지원, 회사방 단위로 선택. 후생노동성 가이드라인이
  "객관적인 기록"을 원칙으로 요구해서 자기신고 단독보다 법적으로 더 안전.
- **근무 스케줄**: 자유/고정/교대 3종 중 회사방 단위로 설정.
- **연차(유급휴가)**: 노동기준법 제39조 기준 근속연수별 자동 부여(6개월 10일 ~ 6년6개월 이상
  20일), 2년 시효, FIFO 소진, **연 5일 의무 사용 미달자 경고**(2019년 시행 규정 대응 --
  이 기능의 핵심 가치). 법정치보다 후하게 주는 회사는 오너가 수동으로 추가 부여.
- **공휴일/휴무일 캘린더**: 업종마다 휴무일 정의가 다를 수 있어(요식업은 명절에도 영업 등)
  회사방마다 직접 등록.
- **반차**: 회사 설정으로 켜고 끔(기본 꺼짐, 종일 단위만).
- **매니저 위임**: 오너 외에 근태 수정/휴가 승인 권한을 사업장 단위(또는 전사)로 위임 가능,
  재위임 허용 여부도 회사가 직접 정함(`allow_manager_delegation`).
- 아직 안 정해진 것: 사원 프로필 테이블 위치, 공휴일 캘린더 사업장별 분리, 초과근무 수당
  계산(범위 밖 명시), 플랜별 기능 차등, 일본 외 국가 노동법 대응.
