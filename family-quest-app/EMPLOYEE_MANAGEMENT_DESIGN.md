# 사원 관리(출퇴근/휴가) 설계 문서 (구상 단계, 2026-08)

`MONETIZATION_DESIGN.md` 2번(컴퍼니퀘스트 B2B 구독)에서 "결제 구조와 묶지 않고 완전히 별도로
설계한다"고 못박아둔 그 영역입니다. 컴퍼니퀘스트(`business-quest-app`)에서만 쓰는 기능이고,
가족방(family-quest-app)에는 해당 없습니다. **아직 코드/DB 전혀 없는 순수 설계 단계**입니다.

일본 시장 우선 출시가 확정된 상태라, 이 문서는 **일본 노동기준법을 기본 전제로 설계**합니다.
다른 국가 노동법 대응은 지금 하지 않고, 나중에 필요해지면 국가별 분기 포인트로 남겨둡니다
(3번 참고).

## 목차

1. 체크인 방식 (GPS + QR)
2. 근무 스케줄 모델 (방 단위 설정)
3. 근태 기록 (+ 공휴일/휴무일 캘린더)
4. 연차(유급휴가) -- 일본 노동기준법 기준 자동 부여/소진 추적
5. 권한/역할
6. UI 개요 (초안)
7. 데이터 모델 요약
8. 아직 정하지 않은 것

---

## 1. 체크인 방식 (GPS + QR)

일본 후생노동성 가이드라인(労働時間の適正な把握のために使用者が講ずべき措置に関する
ガイドライン, 2017)은 근로시간을 "객관적인 기록(客観的な記録)"을 기초로 확인하는 걸 원칙으로
삼습니다 -- 자기신고(버튼만 누르는 자율 체크인)만 쓰는 건 예외적인 경우로만 허용되고, 그마저도
추가 검증 조치가 필요합니다. GPS 위치 기반이나 QR/IC카드는 그 자체로 시스템이 남기는 객관적
기록이라 오히려 법적으로 더 안전한 방식입니다. 실제로 King of Time/jinjer勤怠/ジョブカン 같은
일본 근태관리 SaaS도 이 두 방식을 표준으로 씁니다.

**둘 다 지원하고, 회사방(방)마다 어느 방식을 쓸지 설정**합니다:

- `families.attendance_checkin_method`: `'gps' | 'qr' | 'both'`
- 사업장(worksite)이 여러 개일 수 있는 회사(체인점 등) 대응 -- `business_worksites` 테이블로
  회사방 하나에 사업장 여러 개를 등록:
  - GPS 방식: 사업장 좌표(위도/경도) + 허용 반경(`radius_m`). 체크인 시 클라이언트가 위치를
    보내고, **서버(RPC)에서 Haversine 공식으로 거리 계산 후 반경 안일 때만 기록 인정** --
    클라이언트가 위치를 위조해서 보내도 서버가 걸러내야 하므로 검증은 반드시 RPC 안에서.
  - QR 방식: 사업장별로 고유 토큰이 임베드된 QR 발급(사무실 출입구에 부착/게시), 스캔 시 그
    토큰이 유효한 사업장 코드인지 서버에서 검증 후 기록.
- 체크인 기록에는 어느 사업장에서 체크인했는지 항상 남깁니다 (다지점 회사의 사업장별 인건비/
  출근 통계에 필요).

## 2. 근무 스케줄 모델 (방 단위 설정)

회사마다 근무 형태가 다르므로 하나로 고정하지 않고, 이것도 방(회사) 단위 설정으로 셋 중 고르게
합니다:

- `families.work_schedule_type`: `'flexible' | 'fixed' | 'shift'`
- **자유근무(flexible)**: 정해진 출퇴근 시간 없이, 체크인~체크아웃 사이 시간을 그대로
  근무시간으로 기록. 스케줄 테이블 불필요, 가장 단순.
- **고정근무(fixed)**: `business_schedule_templates`에 표준 근무시간(예: 09:00~18:00,
  휴게 60분)을 등록해두고, 지각/조퇴/초과근무를 그 기준과 비교해서 판정.
- **교대근무(shift)**: `business_shift_defs`(조 이름 + 시작/종료 시각, 예: 오전조/오후조/야간조)로
  근무조를 정의해두고, `business_shift_assignments`(직원 x 날짜 x 조)로 실제 배정.

세 모델 다 최종적으로는 `attendance_records`에 실제 체크인/체크아웃 시각과 계산된 근무시간이
남는 건 동일 -- 스케줄 모델은 "지각/초과근무를 판정하는 기준"만 다르게 제공하는 계층입니다.

## 3. 근태 기록

- `attendance_records`: 사원 1명의 하루 출퇴근 1건.
  - `check_in_at`/`check_out_at`, `worksite_id`, `check_in_method`(`gps`/`qr`/`manual` --
    관리자가 뒤늦게 수기로 정정하는 경우 대비), `status`(정상/지각/조퇴/결근/휴일근무 등),
    `work_minutes`(계산된 실근무시간), `overtime_minutes`
  - GPS 방식일 땐 체크인 당시 좌표도 감사 로그 목적으로 같이 저장 (분쟁 시 근거 자료)
- **휴게시간은 별도 체크인/아웃 없이, 고정/교대 스케줄에 등록된 휴게시간을 자동 차감하는
  방식으로 통일**합니다. 휴게 자체가 회사마다 다르긴 하지만, 그 다름은 이미 스케줄 템플릿
  (`business_schedule_templates`)의 휴게시간 값 자체로 흡수되므로 -- "자동 차감이냐 별도
  기록이냐"라는 기능 단위까지 회사마다 켜고 끄게 하면 얻는 유연성 대비 구현/UI 복잡도가
  안 맞다고 판단했습니다. 자유근무(스케줄 없음)일 땐 애초에 차감할 기준이 없으니 해당 없음.

### 3-1. 공휴일/휴무일 캘린더 (회사방 단위 직접 등록)

업종마다 휴무일 정의가 다릅니다 -- 요식업/서비스업은 명절에도 정상 영업하고, 사무직 회사는
국경일에 쉬는 식으로 정반대일 수 있어서 하나로 고정할 수 없습니다.

- `business_holidays`: `family_id`, `date`, `label`(휴무일 이름, 예: "설 연휴"), `created_by`.
  오너(또는 사업장 관리 권한이 있는 매니저)가 회사방마다 직접 등록.
- 이 캘린더는 두 군데에서 쓰입니다:
  - `attendance_records.status` 판정 -- 등록된 휴무일에 출근했으면 "휴일근무"로 분류(수당
    계산은 범위 밖이지만, 판정 자체는 필요).
  - 고정/교대 스케줄의 초과근무 계산 -- 휴무일엔 애초에 표준 근무시간 기준 자체가 적용 안 됨.
- 사업장별로 다른 휴무일을 쓰는 다지점 회사(체인점 등) 대응은 `worksite_id`(nullable, null이면
  전사 공통)까지 필요한지는 8번 열린 질문으로 남깁니다 -- 1차는 회사방 전체 공통 캘린더로
  시작.

## 4. 연차(유급휴가) -- 일본 노동기준법 기준 자동 부여/소진 추적

일본은 이 부분이 단순 "신청→승인"만으로는 법적으로 부족합니다. 노동기준법 제39조 기준을
그대로 반영합니다:

**자동 부여 규칙** (풀타임, 주 5일 이상 근무 기준):

| 근속기간 | 부여 일수 |
|---|---|
| 6개월 | 10일 |
| 1년 6개월 | 11일 |
| 2년 6개월 | 12일 |
| 3년 6개월 | 14일 |
| 4년 6개월 | 16일 |
| 5년 6개월 | 18일 |
| 6년 6개월 이상 | 20일 (이후 유지) |

- 파트타임(주 소정근로일수가 적은 경우)은 비례 부여(比例付与) 별도 표 적용 -- 주 근무일수
  필드(`weekly_work_days`)를 사원 프로필에 두고 이 표로 분기.
- 부여된 연차는 **발생일로부터 2년 시효** -- 안 쓰면 소멸.
- **연 5일 의무 사용** (2019년 4월 시행): 연 10일 이상 부여받는 사원에 대해 사업주가 최소 5일은
  반드시 사용시켜야 함. 미이행 시 근로기준법 위반(근로자 1인당 30만엔 이하 벌금 대상).

**설계**:

- `employee_profiles.employment_start_date` (근속연수 계산 기준), `weekly_work_days`(비례
  부여 판별용) -- `family_members`를 그대로 확장할지, 회사방 전용 프로필 테이블을 새로 둘지는
  8번 열린 질문.
- `annual_leave_grants`: 부여 1건 = 1행. `granted_on`, `days_granted`, `expires_at`(2년 후),
  `days_used`, `source`(`'auto'`/`'manual'`), 잔여일수는 `days_granted - days_used`로 계산.
- 매일(또는 매월) 배치로 근속연수가 부여 기준일에 도달한 사원을 스캔해서 `source='auto'`로
  자동 부여 -- `send-weekly-summary`와 같은 기존 pg_cron 패턴 재사용.
- **법정 최소치보다 후하게 주는 회사 대응**: 복리후생 차원에서 법정 기준보다 넉넉한 연차를
  주는 회사도 있는데, 이건 별도 정책 스위치를 두지 않고 **오너가 같은 `annual_leave_grants`에
  `source='manual'`로 직접 행을 추가**하는 것으로 커버합니다 -- 법정 자동 부여(`auto`)는
  법 위반을 안 만드는 바닥값으로 항상 그대로 깔리고, 그 위에 회사 재량껏 얹는 구조라
  법정치 밑으로 내려갈 걱정이 없습니다.
- **소진은 FIFO** -- 시효가 먼저 끝나는 부여분부터 차감(자동/수동 구분 없이 시효 순서로),
  시효 관리가 실제 법 취지와 맞음.
- **연 5일 미달 경고**: 부여일 기준 1년 안에 5일 미만 사용한 사원을 오너/매니저 화면에
  경고 리스트로 노출(매니저는 자기 위임 범위 안 사원만) -- 이게 이 기능의 핵심 가치입니다
  (단순 기록이 아니라 실제 컴플라이언스 리스크를 미리 알려주는 것).
- 휴가 신청 플로우는 기존 퀘스트의 "완료 보고 → 승인" 2단계 패턴을 재사용 -- 사원이 날짜
  지정해서 신청 → 오너 또는 그 사원의 위임 범위를 가진 매니저가 승인/반려 (5번 참고).
- **반차(半休, 시간 단위 휴가)는 회사 설정으로 켜고 끔**: `families.half_day_leave_enabled`
  (boolean, 기본값 `false`). 꺼져 있으면 지금처럼 종일 단위만 -- 반차 자체가 필요 없는 회사가
  많아서(특히 소규모) 강제하지 않고, 필요한 회사만 켜서 `leave_requests.unit`(`'full'`/`'half'`)을
  쓰게 합니다. 켜졌을 때 `annual_leave_grants`/`leave_requests`의 일수 단위도 0.5일 단위
  계산을 허용.

## 5. 권한/역할 -- 매니저 위임

`family_members.role`(`'owner'/'member'`)은 그대로 둡니다 -- 방장 자동 위임, 방 나가기 제한
같은 기존 로직이 이미 이 두 값을 전제로 동작 중이라 건드리면 파급 범위가 큽니다. 매니저는 이
role을 대체하는 게 아니라 **member 위에 얹는 추가 권한 레이어**로 설계합니다.

### 5-1. 위임 범위 -- 사업장 단위로 지정 가능 (비워두면 전사)

- `business_manager_grants`: `family_id`, `user_id`(매니저), `worksite_id`(**nullable** -- null이면
  전사 범위, 특정 사업장 id면 그 사업장 소속 사원만), `granted_by`, `granted_at`, `revoked_at`
- 한 사람이 여러 행을 가질 수 있습니다 -- 지점 A/B 매니저는 각각 한 행씩(`worksite_id`=A,
  `worksite_id`=B), 전사 매니저는 `worksite_id`=null인 행 하나. "이 사람의 관리 범위"는 전사
  grant가 하나라도 있으면 전체, 없으면 사업장 grant들의 합집합으로 판정.
- 지점 없는 소규모 회사는 그냥 전사 grant 하나만 쓰면 되므로 사업장 단위 지정을 안 쓰는 경우와
  구분 없이 자연스럽게 커버됩니다.

### 5-2. 매니저가 할 수 있는 일 -- 근태 수정 + 휴가 승인만

- 자기 위임 범위(사업장) 안의 사원 대상으로만: `attendance_records` 수기 정정,
  `leave_requests` 승인/반려.
- 사업장 등록/GPS·QR 재설정, 연차 부여 규칙 변경, 사원 추방(기존 `remove_family_member`) 같은
  민감한 설정은 매니저 권한 밖 -- 오너 전용 그대로 유지.

### 5-3. 매니저 임명 -- 위임 허용 여부를 회사가 직접 정함

- `families.allow_manager_delegation`(boolean, 기본값 `false`): 꺼져 있으면 오너만 매니저를
  임명/해임할 수 있음. 오너가 켜면 매니저도 새 매니저를 임명할 수 있게 됨.
- 켜져 있어도 **매니저가 임명하는 신규 매니저의 위임 범위는 임명하는 매니저 자신의 범위를 벗어날
  수 없음** -- 지점 A 매니저는 지점 A 안에서만 새 매니저를 지정 가능, 전사 매니저는 전사 범위로
  지정 가능. 권한이 통제 없이 퍼지는 걸 막는 안전장치입니다. 취소도 동일한 규칙 -- 오너는 언제나
  아무 grant나 취소 가능, 매니저는 위임이 켜져 있을 때 자기 범위 안의 grant만 취소 가능.
- `granted_by`가 그 자체로 임명 감사 로그입니다 -- 재위임을 허용해도 "누가 이 매니저를
  임명했는지"는 항상 추적됩니다.

## 6. UI 개요 (초안)

- **사원용**: 체크인/체크아웃 큰 버튼 화면(오늘 근무 상태 표시) + 내 연차 잔여일수 + 휴가 신청
  폼 + 내 근태 이력
- **매니저용**: 자기 위임 범위(사업장) 안 사원만 보이는 근태 현황/휴가 승인함 -- 오너용과 같은
  화면을 위임 범위로 필터링해서 재사용
- **오너용**: 전체 사원 근태 현황(캘린더/테이블 뷰), 휴가 신청 승인함, **연 5일 미달 경고
  리스트**, 사업장 관리(GPS 좌표/QR 발급), **공휴일/휴무일 캘린더 관리**, **매니저 위임
  관리**(임명/해임, `allow_manager_delegation` 토글)

## 7. 데이터 모델 요약 (안)

| 테이블 | 용도 |
|---|---|
| `business_worksites` | 사업장(다지점 대응) -- 이름, GPS 좌표+반경, QR 토큰 |
| `attendance_records` | 사원 1명의 하루 출퇴근 1건 -- 체크인/아웃 시각, 방식, 상태, 근무시간 |
| `business_schedule_templates` | 고정근무 스케줄(회사방 단위) -- 표준 출퇴근 시간, 휴게시간 |
| `business_shift_defs` | 교대근무 조 정의 -- 조 이름, 시작/종료 시각 |
| `business_shift_assignments` | 교대근무 배정 -- 사원 x 날짜 x 조 |
| `business_holidays` | 공휴일/휴무일 캘린더(회사방 단위 직접 등록) -- 날짜, 이름 |
| `annual_leave_grants` | 연차 부여 1건 -- 부여일, 부여일수, 시효, 사용일수, 자동/수동 구분 |
| `leave_requests` | 휴가 신청 -- 날짜, 단위(종일/반차), 상태(대기/승인/반려), 승인자 |
| `business_manager_grants` | 매니저 위임 1건 -- 대상 사업장(null=전사), 임명자, 임명/해제 시각 |

`families`에 새로 추가되는 설정 컬럼: `attendance_checkin_method`, `work_schedule_type`,
`allow_manager_delegation`, `half_day_leave_enabled`.

## 8. 아직 정하지 않은 것

- 사원 프로필을 `family_members` 확장으로 갈지, 회사방 전용 테이블을 새로 둘지
- 공휴일 캘린더를 사업장별로 다르게 등록할 수 있어야 하는 다지점 회사 대응 (1차는 회사방
  전체 공통 캘린더, 3-1번 참고)
- 초과근무 **수당 계산**까지 포함할지 -- 이번 설계는 근무시간/초과근무 "시간" 산출까지만이고,
  급여 계산/지급은 완전히 범위 밖 (별도 영역)
- 플랜(Standard/Pro/Premium)별 기능 차등 여부 -- `MONETIZATION_DESIGN.md` 2번의 가격 설계가
  먼저 정해진 뒤에 결정
- 일본 외 국가(한국 등) 노동법 대응 -- 지금은 일본 로직만, 필요해지면 국가별 분기 확장
