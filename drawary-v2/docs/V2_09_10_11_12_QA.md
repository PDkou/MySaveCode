## #11 서랍 칸 수정 — reconstructed list view

- Source: `Drawary_11_FINAL_CONFIRMED_CODE.zip`. `CONFIRMED.md` states the
  interaction model plainly: tap a row → edit; drag the right handle →
  reorder; **no hidden swipe actions**. The bundled `DrawerFieldEditFlow.tsx`
  contradicts this directly -- its list view has no `onClick` on normal
  rows at all, and still implements an old swipe-to-reveal pattern for one
  row ("category"). The bundled `field-edit.css` settles which one is
  current: it carries a `/* V2: no hidden swipe actions */` section with
  `.df-row-tap`, `.df-row-edit-hint`, `.df-list-help`, and
  `.df-row.is-editable` (a 5-column grid with room for the hint) -- none
  of which the given TSX ever renders, and the old `.df-swipe-wrap`/
  `.df-action` rules the TSX *does* use are gone from the CSS entirely.
  So: the CSS is the later revision, the bundled TSX is stale.
- `src/screens/DrawerFieldEditScreen.tsx`'s list view is rebuilt from the
  CSS's own class names/grid column count to match "V2: no hidden swipe
  actions" (a full-row invisible `.df-row-tap` button → edit, plus a `›`
  `.df-row-edit-hint`, plus the `.df-list-help` banner using the exact
  copy from `CONFIRMED.md`'s "안내문" bullet). The edit/detail view and the
  delete-confirm bottom sheet had no such conflict (every class appears in
  both files) and are ported as-is.
- **Functional fix needed to make both interactions coexist**: the
  archive's own `.df-row-tap` rule used `inset:0`, covering the entire row
  including the 40px reorder-handle column; since `.df-handle` had no
  `z-index` of its own, the tap overlay (`z-index:3`) would have silently
  swallowed every click on the handle. Changed `.df-row-tap` to
  `right:40px` (excluding exactly the handle's own width) instead of
  `inset:0`, and gave `.df-handle` `z-index:4` as a second line of
  defense. Verified by clicking the handle's exact bounding-box center and
  confirming it does *not* navigate to the edit screen, then clicking the
  row body and confirming it does.
- Also fixed: the archive's icon paths (`/assets/field_*.webp`,
  `/assets/icon_*.webp`) didn't match this app's real layout
  (`/assets/field-types/...`, `/assets/ui-icons/...`), and the source file
  had several literal `\n` escape sequences embedded as two-character text
  in the middle of lines (not real line breaks) -- a mechanical corruption
  from however this archive was assembled, cleaned up during the port.

## Wiring

All three are reachable as their own routes (`#/new-field`, `#/field-edit`,
`#/creation-complete`) **and** chained from #09's own buttons
("서랍 칸 추가" → #10, tapping a field row → #11, "서랍 만들기 완료하기" → #12).
Each of #10/#11/#12 independently manages its own local demo state (field
list, selected type, options) rather than a shared create-drawer model --
there's no data layer yet (V2-12) to carry a newly added field, an edited
field, or the finished drawer's real field count back into #09 or into
each other. So the chain is real *navigation*, not yet real *data flow* --
flagged here rather than quietly implied by the working links.
