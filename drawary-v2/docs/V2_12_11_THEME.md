## Source of the rules

## What a theme changes
- **Saved** as setting `theme`; put on the page as `data-color-theme` on `<html>` (a copy in localStorage makes the first paint right; the database stays the truth). A data reset returns to lavender.
- **Flat colours**: every lavender-family colour in the CSS (255 hex + 34 rgb values, ~530 uses) is written `var(--tc-xxxxxx, #xxxxxx)` / `rgba(var(--tr-r-g-b, r,g,b), a)`. A theme re-defines them in `src/theme/themes.css` (generated by `scripts/make_theme_css.py`). A colour keeps its role: hue moves to the theme's, strong accents take the theme main colour's saturation/lightness relative to lavender's (so the main button colour is exactly the spec main colour), light tints only change hue so they stay pastel. Rules in `scripts/theme_colors.py`.
- **Artwork**: the accent-coloured pictures (UI icons, field-type icons, bottom-nav parts) have a version per theme in `public/assets-theme/<theme>/` made by `scripts/make_theme_assets.py` — only lavender-hue pixels change (feathered), white/pink/yellow/outline pixels stay. Screens still point at the originals; `src/theme/themedImages.ts` swaps every such `<img>` (and any added later) for the theme's version.
- **Background**: for the four non-lavender themes `body::before` paints the spec background and the cream screen roots go transparent (list in `make_theme_css.py`).

This changes lavender's flat cream (255,249,241) of the approved #38/#39 renders to the spec gradient; the user approved that. The lavender *colours* of buttons/text/icons are unchanged (lavender defines no overrides, the CSS fallbacks are the approved values).

Before the background change, all 54 routes were pixel-identical to before the theme work (one route non-deterministic on its own).

- Sage's main colour is desaturated (S≈20%), so sage accents read grey-green; that is the spec value.
- #39's footer text stays the approved "선택한 테마는 앱 전체의 주요 색상과 장식에 적용됩니다." (user: no need to change it).
- Print/PDF export is not tinted (print CSS has its own palette).
